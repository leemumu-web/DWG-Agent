# 每日一键归档设计

## 目标与边界

每日归档用于把指定业务日期内已经登记为 `available` 的生产文件整理成一个可下载、可审计、可重复验证的交付快照。它是数据控制台的日常整理能力，不替代数据库备份、MinIO 灾备，也不直接推进单个生产批次的 `delivery_archive` 阶段。

归档采用非破坏式策略：不移动、不重命名、不软删除原文件。系统只新增一个 ZIP、一个独立 JSON 清单和一条 MySQL 运行记录。

## 操作流程

1. 管理员或审计员选择业务日期和可选 Bucket，执行预检。
2. 后端按 `Asia/Shanghai` 自然日换算 UTC 查询边界，选择可用文件，排除 `daily-archives/` 下的历史归档产物。
3. 预检返回文件数、源文件总大小、格式/Bucket 分布、清单 SHA-256、失效时间和签名令牌。
4. 管理员确认后提交令牌和客户端幂等键；后端把预检时的文件 ID 快照登记到 MySQL，并投递 `maintenance` 队列。
5. Worker 重新校验文件状态与清单哈希，以流式方式读取当前存储后端并生成 ZIP。
6. ZIP 和 JSON 清单通过统一文件登记与传输流水写入 `dwg-reports/daily-archives/YYYY-MM-DD/`。
7. 前端轮询运行状态，成功后分别提供归档包和清单下载入口；失败时保留稳定错误码和可重新预检提示。

## 防错和恢复规则

- 预检令牌短时有效且带 HMAC 签名，执行范围不能由浏览器改写。
- Worker 使用预检时冻结的文件 ID，不会把提交后新入库的文件静默加入 ZIP。
- 同一操作者的幂等键只对应一次提交；同日期、同范围、同清单的成功归档直接复用。
- 同日期、同范围存在排队或运行任务时复用活动任务，避免双击重复生成。
- 原文件在执行前被删除、元数据发生变化或对象不可读时，本次运行失败，不生成貌似完整的 ZIP。
- ZIP 内文件名为 `<bucket>/<file_id>_<安全化原名>`，消除同名覆盖；根目录内同时包含 `manifest.json`。
- 对象写入失败或数据库事务回滚时，复用统一存储补偿机制移除未登记对象并结算传输流水。

## 数据与接口

MySQL 表 `daily_archive_runs` 保存日期、时区、范围、状态、源清单哈希、冻结文件 ID、统计、任务 ID、两个结果文件 ID、错误与起止时间。

接口位于 `/api/v1/data-admin`：

- `POST /daily-archives/preview`：生成只读预检，管理员和审计员可用。
- `POST /daily-archives`：提交异步归档，仅管理员可用。
- `GET /daily-archives`：分页查看历史。
- `GET /daily-archives/{archive_id}`：查看单次运行详情。
- 结果下载复用 `/api/v1/files/{file_id}/download-url`，不增加旁路权限模型。

## 明确不做

- 不启用 Celery Beat 自动调度；当前为人工一键、维护队列异步执行。
- 不删除或迁移源对象。
- 不宣称本地开发存储为 MinIO；产物写入配置的当前存储后端，生产配置为 MinIO。
- 不把日常归档描述为灾难恢复备份。
