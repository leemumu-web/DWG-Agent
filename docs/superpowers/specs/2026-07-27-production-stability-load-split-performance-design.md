# 生产稳定性、并发压力与拆板性能设计

## 目标

在真实服务器 `192.168.188.50` 上建立可重复、可解释的生产验证体系，证明多账号同时提交时 API、MySQL、MinIO、Celery、ODA、分类和拆板不会丢任务、丢图纸或产生不可恢复的状态；在稳定性门槛全部通过后，以实测数据选择拆板并发参数。

## 原则

1. 先测量、后修改。任何修复或并发调整必须对应可复现的问题、资源瓶颈或性能数据。
2. 使用正式 HTTP API 和真实 DWG、Excel，不直接向业务表造数据，不绕过冻结、分类或拆板阶段。
3. 每个账号使用独立项目、工作流和输入批次；跨账号共享的只有服务器资源。
4. 测试密码只从环境变量读取，报告不得包含密码、令牌、DSN 或对象存储密钥。
5. `super_admin` 的安全限制默认保留。只有合法生产操作被权限错误阻断时，才以最小范围调整并补权限回归。
6. 压力测试产生的数据必须带唯一前缀，测试结束后精确清理；五金手册、账号、角色和系统表不重建。

## 测试分层

### 1. 静态与启动基线

- 校验发布版本、14 个服务健康、容器重启和 OOM 状态、Celery 实际命令、队列配置及数据库连接池。
- 记录 CPU、内存、交换区、磁盘、Docker、MySQL 缓冲池和开放端口。
- 以系统开机时间为日志边界，区分启动等待、关机期间依赖退出和稳态异常。

### 2. 单项目功能基线

使用一个操作员账号完成：

`创建生产项目 → 创建输入批次 → 上传 Excel → 上传 DWG 文件夹 → DWG 转 DXF → 冻结 → 分类 → 拆板 → 下载并核验`

每个阶段保存 HTTP 状态、请求编号、Job 编号、attempt、耗时、输入/输出数量及错误码。下载结果必须可解压，文件名、安全路径、DXF 数量和分类/拆板账本一致。

### 3. 多账号并发矩阵

- 账号：`admin01`、`admin02`、`operator01`、`operator02`。
- 并发档位：1、2、4 个项目；稳定后增加到 8 个项目，但仍由四个账号轮流拥有。
- 每个项目采用同一份只读样本集合，上传时保持真实原名；项目编号添加测试前缀避免冲突。
- 登录按网关安全限流节奏进行；业务提交并发执行，不通过关闭限流伪造高吞吐。
- 记录成功率、阶段 p50/p95、队列等待时间、处理时间、吞吐、重试、429/409/5xx、容器重启和 OOM。

### 4. 拆板并发矩阵

拆板 CLI 当前在一个 Job 内串行处理整批图纸，Celery `worker-dxf-split` 负责多个项目并行。服务器有 16 个低单核性能虚拟 CPU、62 GiB 内存和虚拟旋转盘，因此只比较整批 Job 并发 1、2、4；只有 4 未出现 I/O 等待、尾延迟或失败恶化时才试 6。

每个档位使用相同项目数和图纸数，至少重复两轮。最终参数必须同时满足：

- Job、图纸和产物数量守恒；
- 任务成功或明确进入人工复核，不允许静默丢失；
- 容器重启、OOM、数据库死锁、Celery worker lost 均为 0；
- 可用内存不低于 20%，交换区无持续换入换出；
- CPU 或磁盘 I/O 等待不能长期饱和；
- 总吞吐提高，且 p95 完成时间没有不可接受恶化。

### 5. 长稳与故障恢复

- 30 分钟混合负载：健康查询、列表、详情、下载和小批生产任务。
- 运行中持续采样资源、队列深度、MySQL 连接、Job 状态、容器健康和日志。
- 在无活动业务 Job 时做一次受控重启，确认 MySQL 未就绪时所有后端/worker 等待并恢复。
- 关机期间 MySQL 先退出造成的 worker stopped 落库失败应被识别为关机噪声，不应打印完整 traceback；若测试可稳定复现，则补回归并做容错修复。

## 工具边界

- `scripts/production/workflow_load.py`：真实 HTTP 工作流驱动、并发调度、数量守恒和 JSON 报告。
- `scripts/production/resource_sampler.py`：通过本机 Docker/MySQL 只读采样；由 SSH 在服务器运行，不包含远端地址或密码。
- `scripts/production/README.md`：样本准备、环境变量、渐进负载、清理与判定说明。
- `backend/tests/infrastructure/test_production_load_tools.py`：锁定参数校验、脱敏、统计、数量守恒和失败退出行为。

## 报告与判定

每轮报告只包含：

- 测试版本、样本摘要、账号角色、并发档位；
- 每阶段成功数、失败数、p50/p95、吞吐；
- 输入、转换、分类、拆板和下载数量；
- CPU、内存、交换区、磁盘 I/O、MySQL 连接、队列峰值；
- 明确错误码、受影响项目和是否需要修复；
- 参数结论及证据。

没有可复现问题时不修改业务代码。发现问题后先补能稳定失败的测试，再修根因、跑完整门禁、构建新加密版本、通过 SSH 发布并重复相同压力矩阵。
