# CAD 双向转换控制台生产易用性修复设计

## 背景与证据

本设计只覆盖 `DWG -> DXF` 与 `DXF -> DWG` 两个转换控制台的提交、状态展示和文件夹操作，不改变 ODA 转换算法。

2026-07-18 对本机 Nginx `:8080`、FastAPI `:8010` 和 MySQL 运行数据的检查确认：

- 页面曾显示“成功 802 / 859、失败 35、处理中 0、96%”。百分比来自所有 Job 的阶段进度平均值，失败 Job 残留的 30% 或 70% 被误算为总体转换进度。
- 文件列表先返回，全部文件与 Job 分页查询稍后返回，导致首屏短暂显示统计为 0、文件“未转换”，之后才跳到真实状态。
- 大范围页面为计算统计与最新 Job，需要拉取全部源文件并按每 200 个文件拆分 Job 请求；加载期间没有明确的汇总加载态。
- 多分片任务提交使用 `Promise.all`。某一分片失败时，调用方只收到整体异常，无法区分已经成功提交和仍待提交的文件。
- 文件夹上传会逐文件吞掉失败，只返回成功数；上传成功但任务提交失败时，用户不能清楚判断文件是否已经保存。
- 文件夹删除先在前端分页获取当前扩展名的文件 ID，再调用普通批量文件删除；这会遗漏同批次生成结果，并绕过已有文件夹语义。
- 文件夹选择后的打包和删除操作栏位于整个文件夹网格之后；文件夹较多或移动端使用时很难发现。
- 文件夹卡片用可点击 `div` 打开，不能通过键盘可靠操作。
- 已成功行把源文件标签改成目标格式，出现 `.dwg` 文件被标为 `DXF` 的含义冲突。

## 目标

1. 提交结果可核对：明确区分上传、提交、部分成功和待补交。
2. 进度可信：百分比、数量和任务状态表达同一事实。
3. 文件夹操作易发现，并正确处理单个或多个文件夹。
4. 删除语义安全：整批删除源文件与生成结果，不产生部分删除或 worker 写回。
5. 两个转换方向共享同一套行为与测试。

## 非目标

- 不修改 DWG/DXF 转换引擎、ODA 分片和 worker 并发参数。
- 不重做整个管理端视觉系统。
- 不把文件夹改造成新的数据库实体；继续使用 `StoredFile.batch_name` 作为批次边界。
- 不删除真实生产数据作为验证手段；删除测试使用隔离 fixture。

## 方案选择

采用聚焦生产修复：改进前端状态模型，并增加一个多文件夹原子删除 API。相比只在前端循环调用现有接口，它能给出确定的全成或全败语义；相比重做转换控制台，改动范围小且可快速回归。

## 前端状态与进度

### 加载状态

文件页数据分为列表、范围文件、最新 Job、文件夹四组。范围文件或最新 Job 未完成前：

- 汇总区域显示加载状态，不显示 0 或推断出的“未转换”。
- 表格中文件本身可以先展示，但转换状态显示“正在加载状态”，不能显示“未转换”。
- 查询失败时保留已加载的文件，并在汇总区域给出可重试错误；不能把失败解释为没有 Job。

### 汇总口径

对当前范围中的每个源文件只使用最新 Job，分类为：

- `succeeded`：转换成功；
- `active`：`pending`、`queued`、`running`、`validating` 或 `waiting_cad_worker`；
- `failed`：失败或取消，需要重新提交；
- `unsubmitted`：没有 Job，需要提交；
- `stuck`：排队超过现有阈值且没有进度，归入需要重新提交。

成功进度按以下公式计算：

```text
(成功文件数 * 100 + 活动任务的阶段进度之和) / 范围文件总数
```

失败、取消、卡住和未提交文件贡献 0，避免失败任务残留进度抬高百分比。界面同时显示成功、失败、处理中、待提交数量；操作按钮使用“提交/重试 N 个”，不再使用含义模糊的“继续任务”。

源文件标签始终显示源格式，转换结果由状态列与目标格式操作表示。

## 上传与任务提交

上传和提交是两个独立阶段：

1. 上传阶段记录匹配文件总数、成功数、失败数和成功文件 ID。
2. 提交阶段对成功上传的文件 ID 去重、按后端 200 个 ID 的限制分片，并以有限并发或顺序提交。
3. 每个提交分片独立记录结果，最终返回已提交 Job、未提交文件 ID 和错误摘要，不能由单个失败覆盖已成功分片。
4. 页面反馈明确显示“上传成功 N，提交成功 M，待补交 K”；上传失败和提交失败分别给出下一步。
5. 上传、文件夹上传或压缩包处理期间，相关入口统一进入忙碌状态，防止重复选择和重复提交。
6. 补交只针对当前最新状态为 `failed`、`cancelled`、`stuck` 或 `unsubmitted` 的文件；先刷新权威状态，再构造请求，避免重复创建成功或活动任务。

网络超时后前端先刷新文件与最新 Job，再判断待补交集合，不直接重放不确定的请求。

## 文件夹交互

- 文件夹标题区提供全选、取消选择和已选数量。
- 选择后操作栏紧邻标题区并保持可见，不再放在完整网格之后。
- 文件夹名称区域使用可聚焦的语义按钮，支持 Enter 和 Space 打开；复选框仍只负责选择。
- 长名称保持完整 tooltip 和可截断布局。
- 打包下载继续允许选择源格式、结果格式和 ZIP 名称；准备文件 ID 时显示忙碌状态，失败时保留选择以便重试。
- 单个与多个文件夹使用一致的确认文案，明确“源文件、生成结果及活动任务都在范围内”。

## 多文件夹原子删除

### API

新增 `POST /api/v1/files/batches/bulk-delete`，请求体包含去重前的 `batch_names`。Schema 要求 1 至 100 个非空名称，每个名称遵守现有批次名称长度边界。

响应返回：

```json
{
  "deleted_batch_count": 2,
  "deleted_file_count": 320,
  "cancelled_job_count": 4
}
```

### 服务端事务

1. 对名称去重，查询所有非删除文件；源文件和生成结果都按 `batch_name` 纳入。
2. 在写入前确认每个请求文件夹均存在，并验证当前用户对每个文件都有删除权限。
3. 查询这些文件关联的活动 DWG/DXF 转换 Job，在同一事务内按现有状态机取消。
4. 对全部文件执行现有软删除、预览失效、传输账本和审计逻辑。
5. 所有校验和写入在同一数据库事务内完成；任意错误回滚全部文件夹。
6. worker 后续提交结果时必须继续受 Job `status + attempt` 条件保护，已取消任务不能写回结果。

请求中包含不存在、已删除或无权限文件夹时，整批返回错误且不改变任何文件夹。名称重复只处理一次。

### 前端行为

- 确认框显示文件夹数量、已知文件总数以及前几个文件夹名称，超出部分显示省略计数。
- 请求进行中锁定选择、打开、上传、打包和删除入口。
- 成功后清空选择并刷新文件、文件夹、Job 和汇总。
- 失败后保留选择并显示后端可操作错误；随后刷新权威状态，避免界面停留在旧数据。

## 错误处理

- 表格失败状态提供简短原因 tooltip，并保留“重新提交”操作。
- 不向前端暴露 traceback、主机路径或 child stderr；继续使用后端安全错误消息。
- 上传或提交的逐项错误只展示有限样本和总数，避免大批量错误淹没界面。
- 删除错误区分不存在、权限不足、活动状态冲突和服务器失败，并给出刷新或联系管理员的下一步。

## 测试与验收

### 前端

- 初始加载不显示假 0 或假“未转换”。
- 成功、活动、失败、未提交混合状态的百分比和数量一致。
- 失败 Job 的 30%/70% 残留进度不计入成功进度。
- 分片提交部分失败时保留已提交结果，并显示待补交数量。
- 上传与提交失败文案可区分，操作期间不能重复触发。
- 文件夹操作栏位于网格之前；全选、取消和键盘打开可用。
- 单个和多个文件夹删除都只发出一次原子批删请求。
- DWG -> DXF 与 DXF -> DWG 两个页面运行同一套参数化测试。

### 后端

- 单文件夹与多文件夹删除成功并返回准确计数。
- 重复名称只处理一次。
- 任一文件夹不存在或无权限时全部回滚。
- 事务中途异常时全部回滚。
- 源文件、生成结果和预览登记一起软删除。
- 关联活动任务被取消，旧 worker 不能写回结果。
- 超过数量限制或空名称返回 422。

### 验证门禁

执行聚焦后端测试、前端生产构建、相关 Playwright 测试、完整后端 pytest、ruff、文档生成与 `make docs-check`。最终再通过本机 Nginx `:8080` 实际浏览器检查两条转换页面；不以单元测试替代真实页面验证。
