# 已分类 DXF 直接拆板设计

## 目标

拆板阶段只使用上一阶段已经冻结并持久化的分类结论。BH 文件直接进入 BH
拆板核心，BOX 文件直接进入 BOX 拆板核心；Stage 不再读取 DXF 文字并重复判断
型材族。

## 已确认事实

- `b8302c0` 是约 4.3 万行的 Steel DXF Split 1.5.2 运行时 PR，已经位于
  `main` 的祖先链。
- 该 PR 的真实 `2b1-cb-56` BOX 样本可以自动验收，并生成正常拆板、余量增长、
  报告和预览。
- 当前生产失败不是拆板算法缺失，而是 PR 之后修改 CLI 造成 BOX 发布认证摘要
  与实现不一致。
- 当前 Stage 只有 BH、BOX 两个拆板领域核心，没有 BT 独立拆板核心。
- 分类运行已经为每个可进入下一阶段的文件持久化 `part_type`、分类处置和来源。

## 输入合同

后端从当前分类运行生成不可变 JSON 清单。清单只允许以下结构：

```json
{
  "schema": "STEEL-DXF-CLASSIFIED-SPLIT-INPUT-1.0",
  "items": [
    {"file_name": "构件1.dxf", "family": "BH"},
    {"file_name": "构件2.dxf", "family": "BOX"}
  ]
}
```

CLI 在处理前冻结输入目录，并验证：

- 清单 schema 正确；
- `items` 中只有 `file_name`、`family`；
- family 只能是当前确有领域核心的 `BH` 或 `BOX`；
- 文件名必须是安全的第一层 DXF 文件名；
- 输入目录和清单必须一一对应，不得缺失、重复或夹带文件。

分类为其他类型的文件不交给拆板 CLI，不伪装成 BH/BOX，也不在 Stage 内进行
回退判型。

## 业务分派

`pipeline` 暴露显式族入口：

```python
split_classified_dxf(input_path, output_dir, options, *, family)
```

该函数不加载 DXF 做型材识别。`family == "BH"` 时只调用 `split_bh_dxf`；
`family == "BOX"` 时只调用 `compile_box`。两者之后继续共用现有成对输出、
焊接余量、独立校验、人工复核和原子发布逻辑。

删除 `profile_detection.py` 及所有运行时引用。输出报告中的 `family` 仍由领域
核心产生，后端独立校验它与上游分类结论一致；这是一致性核验，不是重新分流。

## 批次和进度

混合 BH/BOX 批次仍由一个 CLI 进程处理。CLI 按冻结输入顺序读取清单中的明确
family，逐图上报进度并隔离单图异常。所有成功 BH 结果共同生成一份项目级
`BH拆板信息表.xlsx`；只有 BOX 时生成表头为空的合法台账。

## 错误处理

分类清单不完整、类型不支持、文件不一一对应时，批次在调用算法前失败，并返回
可操作的中文错误。领域核心报告出的人工复核仍进入人工复核，不转换成服务器
异常。单图算法异常仍形成该图的 `failed` 结果，不影响其他图完成。

## 发布可信性

删除分流器和修改入口会改变受保护实现，不能直接替换摘要。使用完整上游分支的
20 对冻结 BOX 人工样本重新执行发布门禁，确认：

- 10 对校准集和 10 对验收集全部通过；
- 人工拆板后文件只用于离线比较，不进入生产决策；
- 新认证绑定删除分流器后的当前实现；
- BH 冻结样本回归同时通过。

## 稳定性和性能验收

完成代码后依次验证：

1. 单元测试证明错误 family 不能进入领域核心。
2. 混合 BH/BOX 批次证明每个文件只进入分类指定的核心。
3. 取消或服务重启后，关联 Job 已结束的 `running` 拆板运行被收口。
4. 正式 HTTP 创建执行，真实 worker 消费任务，结果写入对象存储和数据库。
5. 下载并重新打开正常 DXF、余量 DXF、JSON 报告和 BH 台账。
6. 页面能读取同一批次及明确错误。
7. 记录成功批次耗时、吞吐、峰值资源；以成功拆板而非快速失败衡量性能。
