# 北京时间全链路迁移设计

## 目标

把生产环境的容器本地时区、MySQL 会话时区、应用业务时间和 Celery 调度时区统一为 `Asia/Shanghai`，并把现有按 UTC 墙上时间保存的 MySQL `DATETIME` 数据转换为同一时刻对应的北京时间。

迁移必须保留两个现有项目、用户、文件元数据、对象存储内容和审计记录。当前上传完成前不得重启 Nginx、后端或数据库。生产写入维护窗目标为 2–5 分钟；如果任一前置检查不满足，迁移不开始。

## 已确认现状

- 宿主机、15 个业务容器、Python 运行时和 MySQL 当前均显示 UTC。
- MySQL `@@global.time_zone` 与 `@@session.time_zone` 均为 `SYSTEM`，`@@system_time_zone` 为 `UTC`。
- Celery 当前使用 `timezone=UTC`、`enable_utc=True`。
- 业务库含 129 个 `DATETIME` 列，没有 `TIMESTAMP` 列。无时区列不能依靠修改 MySQL 会话时区自动转换。
- 当前有两个项目和两个已登记文件；文件夹 Multipart 上传在请求提交前可能尚无 `file_transfers` 或 `files` 记录。

## 方案

### 时间语义

- 应用对外返回的业务时间统一为带 `+08:00` 偏移的 ISO 8601 字符串。
- MySQL `DATETIME` 统一保存北京时间墙上时间。历史值在维护窗内统一增加 8 小时。
- 令牌、签名到期时间和消息协议中的 Unix epoch 继续代表绝对时刻；只改变其本地格式化和数据库墙上时间表示，不改变有效期长度。
- Celery 的业务调度时区改为 `Asia/Shanghai`。消息传输仍保留 Celery 的 UTC 标准化能力，避免跨进程 ETA 解释不一致。

### 配置与代码

- 容器环境增加 `TZ=Asia/Shanghai`，并确保镜像能够读取对应 zoneinfo；不通过复制宿主机可变文件形成隐式依赖。
- MySQL 启动参数增加 `--default-time-zone=+08:00`，并在连接建立时校验会话时区为 `+08:00`。
- 将应用中直接写入数据库的 UTC 墙上时间收口到统一的北京时间时钟函数。显式需要 epoch/签名计算的代码继续使用绝对时间，不混用数据库墙上时间。
- FastAPI 响应序列化必须携带 `+08:00`，前端继续使用浏览器本地格式化，不再猜测无偏移时间字符串。
- Celery 配置使用 `Asia/Shanghai`，并用测试证明定时边界、过期判断和任务持续时间不发生 8 小时漂移。

## 测试先行

实施前先增加失败测试，覆盖：

1. 业务时钟生成带 `+08:00` 的当前时间。
2. API 时间字段包含明确的 `+08:00` 偏移。
3. MySQL 连接会话时区不是 `+08:00` 时启动或就绪检查失败。
4. 令牌有效期、幂等窗口、任务超时和保留期在迁移前后保持相同秒数。
5. Celery 的北京时间自然日调度边界正确。
6. Compose 渲染结果为所有相关容器提供 `TZ=Asia/Shanghai`，MySQL 含默认时区参数。
7. 数据迁移脚本只处理 `DATETIME` 列，可重复检测，且不会对已迁移库再次增加 8 小时。

## 生产迁移步骤

1. 在本地完成代码、配置、迁移脚本和自动化测试，构建新镜像；服务器不变。
2. 只读观察两个项目，直到没有活动 HTTP 上传、没有 `prepared`/`in_progress` 文件传输，并且数据库与 MinIO 已提交对象一致。
3. 生成迁移前清单：项目、用户、文件、传输、工作流、作业、对象数量与总字节数；记录健康状态和磁盘余量。
4. 临时阻止新的业务写入，等待在途请求归零。读取仍可保持；若无法可靠阻止新写入，则进入明确的短维护页。
5. 创建可恢复的 MySQL 一致性备份，并验证备份可读；保留 MinIO 数据卷，不移动对象。
6. 在单个数据库事务或受控分表事务中转换历史 `DATETIME` 值，并写入一次性迁移标记。任何语句失败立即回滚。
7. 以数据库和对象存储优先的顺序切换：MySQL → MinIO → 后端 → workers → Nginx。每一层健康后才进入下一层。
8. 恢复写入并执行真实的小型读写验证；不得使用现有项目制造测试数据。

## 验证门槛

- 容器 `date`、Python 本地时间、MySQL `NOW()` 和 Celery 配置均为北京时间；同一时刻差值小于 2 秒。
- MySQL `UTC_TIMESTAMP()` 与 `NOW()` 相差 8 小时，所有新连接的 `@@session.time_zone` 为 `+08:00`。
- 迁移前后的 epoch 对照证明每条抽样记录表示同一绝对时刻。
- 项目、用户、文件、传输、工作流、作业、对象数量与总字节数和迁移前清单一致。
- 15 个容器全部健康，主页、`/nginx-health`、`/health/ready` 返回 200。
- 两个现有项目可正常打开，已上传文件可读取；无失败传输、补偿待办、缺失对象或大小不一致。
- 迁移脚本二次运行必须拒绝或空操作，不能再次增加 8 小时。

## 回滚

- 在恢复业务写入前失败：停止新栈，恢复 MySQL 备份和旧 Compose/镜像，按 MySQL、MinIO、后端、workers、Nginx 顺序启动。
- 恢复写入后发现时间语义错误：立即重新进入维护窗，保留故障现场清单，再用迁移前备份回滚；不对生产行做临时减 8 小时修补。
- MinIO 对象内容不参与时间值转换，回滚不得删除或重建对象存储卷。

## 非目标

- 不修改历史文件内容、SHA-256、对象键或用户凭据。
- 不借本次迁移清理项目、审计日志或其他业务数据。
- 不在两个上传请求仍活动时进行容器重建或数据库切换。
