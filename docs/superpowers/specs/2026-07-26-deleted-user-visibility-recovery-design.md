# 已删除用户可见与恢复设计

## 问题

用户采用软删除：数据库保留用户名和历史关联，但用户列表过滤了 `deleted` 状态。因此管理员创建同名用户时会收到“用户名已存在”，却无法在页面中找到占用该用户名的记录。

## 决策

1. 管理员用户列表默认包含正常、禁用和已删除账号，并用“已删除”状态明确区分。
2. 已删除账号不得直接编辑角色、重置密码、禁用或再次删除，只提供“恢复”操作。
3. 恢复后状态设为“已禁用”，同时清空 `deleted_at` 并设置“必须重置密码”。后端在管理员完成密码重置前拒绝启用，前端同步禁用启用按钮；管理员还需核对角色后再明确启用。
4. 不允许创建请求自动复用或覆盖已删除账号，避免历史任务、文件、审计记录与新人身份混淆。
5. 恢复操作仅允许管理员，写入 `users.restore` 审计记录；正常或禁用账号不能调用恢复接口。
6. 现有唯一超级管理员保护保持不变。

## 数据流

`GET /api/v1/users` 返回所有状态的账号。管理员在前端看到已删除行后，可调用 `POST /api/v1/users/{id}/restore-requests`。后端在数据库行锁下确认账号确实为已删除状态，将其恢复为禁用并清除删除时间，然后记录审计日志并原子提交。

## 验证

- 后端测试覆盖：列表包含已删除账号、恢复后为禁用、删除时间清空、审计存在、非管理员被拒绝、未删除账号不可恢复。
- 前端契约测试覆盖：已删除行显示恢复入口，并调用专用恢复接口。
- 构建、权限回归、真实容器部署和浏览器端到端验证均通过后才交付。
