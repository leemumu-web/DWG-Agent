# r36 工人报错体系与生产功能门禁设计

日期：2026-07-31  
状态：已确认，待实施

## 1. 目标

r36 要同时解决两类生产问题：

1. 工人看到的报错必须准确说明原因和下一步，不展示后端日志、英文异常或稳定错误码，也不能把确定性错误误导成“稍后重试”。
2. 容器健康不能代替业务功能可用。生产部署必须在启动前和启动后确认分类、拆板、Excel 第一阶段、Excel 第二阶段、余料库等已批准功能确实启用并可调用。

本次不改变现有后端错误信封，也不把界面动作元数据加入所有 API。稳定错误码继续作为程序内部契约和管理员排障依据，由前端集中翻译成工人可理解的中文语义。

## 2. 已确认根因

请求 `da8dd260b41c8262947b8e2c0d9da64d` 对应：

- 请求：`GET /api/v1/workflows/8/stages/excel_stage2/preflight`
- HTTP 状态：503
- 稳定错误码：`EXCEL_STAGE2_PIPELINE_DISABLED`
- 后端运行环境缺少 `EXCEL_STAGE2_PIPELINE_ENABLED`
- 设置默认值为 `false`，所以后端按契约拒绝执行
- Excel 第二阶段 worker 虽然健康，但健康 worker 不能覆盖关闭的功能开关

因此“服务当前未启用”不是前端凭空误报；误导来自两个后续环节：实际运行配置与生产模板发生漂移，以及前端把所有 5xx 统一建议成“稍后重试一次”。

## 3. 用户界面契约

每个前端 API 错误统一解析为以下语义：

- `message`：有界、无技术细节的中文原因
- `recovery`：工人下一步动作
- `kind`：错误类别
- `retryable`：当前界面是否允许重试
- `requestId`：请求编号，供管理员定位
- `code`：稳定错误码，仅供程序判断、测试和管理员排障，不在工人界面直接展示

错误卡片固定按“标题 → 原因 → 处理建议 → 允许的动作”呈现。不能根据后端错误码生成卡片标题，不能显示 Python、SQL、容器、内部路径、HTTP 原文或英文异常。

### 3.1 错误类别与恢复动作

| 类别 | 典型情况 | 工人提示 | 自动重试 | 手工重试 |
| --- | --- | --- | --- | --- |
| 输入问题 | 400、413、415、422、Excel 输入问题 | 修正指出的字段、工作表、文件或批次规模 | 否 | 否 |
| 登录失效 | 401 | 重新登录，避免重复提交 | 否 | 否 |
| 权限不足 | 403 | 确认项目归属；确需权限时联系管理员 | 否 | 否 |
| 资源不存在 | 404 | 刷新并确认批次或文件是否仍存在 | 否 | 否 |
| 状态冲突 | 409 | 刷新状态，按当前阶段继续 | 否 | 否 |
| 功能未启用 | `*_PIPELINE_DISABLED`、`REMNANT_INVENTORY_DISABLED` | 当前部署未开启该功能，请联系管理员检查配置和对应 worker | 否 | 否 |
| 容量或限流 | 429、存储空间不足 | 等待队列、减小批次或联系管理员清理空间 | 否 | 仅在条件恢复后 |
| 临时网络/网关故障 | 无响应、502、504、未知临时 503 | 先刷新状态，确认是否已受理，再有限重试 | 最多有限次数 | 是 |
| 服务器内部故障 | 500 或未知服务错误 | 保留请求编号并联系管理员 | 否 | 默认否 |

已知确定性错误优先于 HTTP 状态。比如 `EXCEL_STAGE2_PIPELINE_DISABLED` 即使是 503，也必须归入“功能未启用”，不能落入通用 5xx 重试逻辑。

### 3.2 重试约束

- React Query 全局重试改为调用统一判定函数。
- 只有连接中断、超时、502、504和没有稳定确定性错误码的临时 503可以有限自动重试。
- 功能关闭、输入问题、权限、资源不存在、状态冲突不得自动重试。
- `ApiErrorAlert` 只有在错误判定为可重试时才渲染重试按钮；业务额外动作不受影响。
- 超时后首先刷新任务状态，避免已经入队的长任务被重复提交。

## 4. Excel 阶段适配

### 4.1 Excel 第一阶段

- 运行前检查错误标题固定为中文业务标题，禁止使用 `error.code`。
- 输入校验失败继续展示结构化工作表、行、列、字段问题。
- 功能未启用时提示管理员检查 Excel 第一阶段开关和 worker，不提供无效“重新检查”。

### 4.2 Excel 第二阶段

- 预检继续显式关闭查询级自动重试。
- `EXCEL_STAGE2_PIPELINE_DISABLED` 显示为生产配置问题，不提示稍后重试，不显示“重新检查”。
- 开关恢复、服务重新启动后，页面刷新会重新执行预检。
- 开关打开但输入缺失时，仍按真实输入/流程状态错误提示，不得伪装成服务未启用。

### 4.3 BH 左右进预审核

同步预审核必须在返回 `ready=true` 前证明：

- 当前工作流确实处于 Excel 第二阶段，且模板要求的 `stage1_excel` 与 `classified_dxf` 已由当前 attempt 形成；
- 第一阶段 Job 属于当前项目、状态成功、attempt 与阶段绑定一致，且当前 attempt 只有一个正式 `stage1_excel`；
- 第一阶段 AnalysisResult、工作流产物和文件登记指向同一个 `.xlsx`，result 元数据中的产物类型和 attempt 一致；
- 第一阶段正式 Excel 对象在文件存储中真实存在，登记大小与对象大小一致；
- 当前分类运行属于同一工作流和项目，绑定当前成功分类 Job attempt；
- 分类运行摘要、分类 Job 参数和当前冻结输入批次的 `manifest_sha256` 三者完全一致，旧分类结果不能进入新输入；
- BH 类型统计与分类账实际 BH 行数一致，单批不超过 5000，所有 BH 条目获准进入下一阶段，文件登记唯一、扩展名/名称/规格/摘要完整；
- 预审核只读，不创建 Job、不绑定 attempt、不写业务数据。

同步 GET 不逐张下载并解析最多 5000 张 DXF，否则页面刷新会重复占用 CPU，并可能让预审核自身超时。正式任务必须在写 Excel 前完成第二层审核：重新校验全部冻结摘要，逐张下载并核验大小与 SHA-256，完整运行 Reader，阻断重复零件号，再由 Excel 第二阶段做三方规格、板件角色、左右进和下料长度校验。Reader 不可靠或 Excel 缺图属于可审计业务结果：相关字段留空或沿用第一阶段基线并进入精炼人工提示，不能编造左右进。

前端的成功文案必须区分“来源与冻结账本已通过预审核”和“逐图读取已完成”，不能在正式任务运行前宣称图纸几何已经校验。

## 5. 生产配置与发布门禁

生产运行文件必须显式包含并设置：

- `DXF_PIPELINE_ENABLED=true`
- `DXF2DWG_PIPELINE_ENABLED=true`
- `DXF2EXCEL_PIPELINE_ENABLED=false`
- `DXF_CLASSIFICATION_PIPELINE_ENABLED=true`
- `DXF_SPLIT_PIPELINE_ENABLED=true`
- `EXCEL_FINAL_PIPELINE_ENABLED=true`
- `EXCEL_STAGE2_PIPELINE_ENABLED=true`
- `REMNANT_INVENTORY_ENABLED=true`

本地 Compose 检查和服务器部署检查都必须验证这些生产约束。不能依赖设置默认值，也不能只验证变量存在。

启动后的 smoke 除网关、API、MySQL、MinIO 健康外，还要读取受保护的系统健康接口并核验已批准功能的运行时值。余料库继续执行真实 MySQL 登记、MinIO 写入/读取/清理闭环。这样可以识别“容器全健康、功能却关闭”的假健康状态。

## 6. 测试策略

### 6.1 前端

- 为稳定错误码、HTTP 状态、网络错误、超时和 Blob 下载错误建立表驱动测试。
- 断言功能未启用不允许重试，未知临时 503按策略处理。
- 断言英文/技术异常被中文安全文案替代。
- 断言请求编号保留、技术错误码不进入工人界面。
- 浏览器验证 Excel 第一/二阶段错误卡片的标题、建议和按钮状态。

### 6.2 后端与部署

- 现有错误信封和稳定错误码契约保持通过。
- `.env.docker.example` 生产开关测试补齐 Excel 第二阶段和余料库。
- Compose 与服务器部署脚本测试覆盖缺失、错误值和运行时漂移。
- r36 启动后实测系统健康接口、Excel 第二阶段预检、余料库数据库/对象存储闭环。

### 6.3 生产业务回归

- 工作流 5、6、8 的页面、预检、阶段状态和现有产物下载。
- 管理员与操作员同时读取/操作各自有权限的生产项目。
- 分类、拆板和 Excel 阶段在队列工作时不因退出登录中断。
- 余料库在加密镜像内仍能完成 MySQL 与 MinIO 交接。

## 7. r36 发布与回滚边界

1. 先完成测试、前端构建、加密镜像检查和 r36 包校验。
2. 更新本机生产运行配置，保留现有密钥、MySQL、MinIO 和应用数据卷。
3. 使用现有 Compose 项目替换 r35 容器，等待全部 15 个服务健康。
4. 完成业务功能门禁、Excel 第二阶段和余料库真实验收后，删除 r35 旧容器和旧镜像。
5. 不执行 `down -v`，不删除任何业务卷，不清空数据库或对象存储。
6. 若 r36 验收失败，停止清理旧镜像，修复后重新构建；数据卷继续原地保留。

## 8. 非目标

- 不向工人展示稳定错误码或后端日志。
- 不为 r36 全面改造所有后端 API 的错误结构。
- 不用自动重试掩盖确定性配置、权限、输入和流程状态错误。
- 不以容器健康数量代替业务功能可用性。
